# Windows首次Loader接入步骤（历史）

本文件保留首次接入Loader的过程和排障记录。该客户端后来已成功进入Loader，并完成真实Renderer和开发版UI验证；本文件不是要求现在再次重启的操作指令。继续验收先核对现有会话，最新状态见[当前状态](../当前状态.md)。

首次检查时应用未启用CDP。Loader要求关闭运行中的Codex后通过其启动流程进入测试会话；此动作会中断聊天执行，应在明确需要重建环境时按当时进程重新核对。不得把独立App Server当作Renderer通过的证据。

用户已在本聊天明确批准提交后安排重启，此授权持续有效。`restart-windows.mjs` 提供原生 Windows `--check` 与 `--arm` 两步入口，参数依次为固定 Loader 源码目录、独立注册表目录、诊断输出目录和已确认的 Codex 主进程 PID。`--arm` 创建独立监督进程，30 秒后请求正常关闭；窗口关闭失败即停止；45 秒未退出则按下述非强制进程树路径继续，最终超时停止，不强杀应用。监督进程使用 Windows 包接口取得安装信息，再复用固定 Loader 的包校验、启动、CDP 所有权校验、注入和生命周期；这是绕过受保护目录枚举限制的启动适配，不修改上游源码。

2026-11-06 实测：首次监督进程返回 close-timeout，已核对进程确实退出；Codex 主进程仍在，未启用 CDP。改为窗口关闭等待 45 秒后补充 `taskkill /PID <已核对PID> /T` 的非强制退出请求，再等待最多 15 秒；始终不使用 `/F`。总等待仍有上限，不能仅凭发出退出请求宣称重启成功。

重启状态保存在所选输出目录的 `restart-state.json`，仅存状态、进程号和本地 CDP 端口；本地诊断目录不入库。恢复聊天后先核对记录中的监督进程确实仍存活和端口状态，不能只凭文件宣称启动成功。工作目录下重新获取的参考源码也应放在忽略目录；项目测试使用 `bun run test`，避免把参考项目测试自动纳入本项目矩阵。

## 重启前准备

1. 保持项目工作树干净，保留当前开发分支，执行 `bun run check`、`bun run test`、`bun run build`。探针包在 `dist/probe`，不依赖全局配置，不修改安装包。
2. 使用已经审阅的固定 Loader 源码 b6ec28c69af12e9667f57d19823fb46d225756e4（package 0.6.0），原生 Windows Node 22+。不要改用未经审阅的 latest 安装器。临时调研源码可能被系统清理，缺失时按该 commit 重新获取并审阅。
3. 选择独立测试数据目录，不复用生产 Loader 配置；安装探针前确认只启用该探针，默认示例 UI 保持禁用。上游 Node 开发宿主不具有 Native Host 的全部安装和自动更新能力，本轮只验证 P0。

## Loader 命令

下面在原生终端运行；将变量设置成当前机器实际路径，文档不保存用户目录或会话信息。准备脚本只初始化空的独立目录并禁用上游默认示例（上游 CLI 默认会启用它），不启动应用。`run --live` 需要所有 Codex 窗口已经正常关闭。

```powershell
# $NodeExe：原生 Node 22+；$LoaderRoot：固定 Loader 源码目录
# $ProbePackage：构建后的 dist/probe；$ProbeData：独立的临时测试目录
& $NodeExe "$ProjectRoot/tools/probes/prepare-loader.mjs" $LoaderRoot $ProbePackage $ProbeData
& $NodeExe "$LoaderRoot/src/cli.mjs" scripts --data-dir $ProbeData
# 正常关闭 Codex 后执行；不要强杀仍在运行的聊天或任务。
& $NodeExe "$LoaderRoot/src/cli.mjs" run --live --data-dir $ProbeData
```

重启后回到本聊天继续。Loader 生命周期日志应包含 anchors、capabilities、markers 和 renderer-wham 或有限错误码。若 anchors 为 missing/ambiguity/space/structure，不强行插入；根据实际语义 DOM 更新独立适配规则，再重新验证。

## 实机采集顺序

1. 确认客户端 build、OS/架构、主题、缩放、语言，内存确认账号及工作区归属。
2. Renderer 额度与独立 App Server、原生 Usage 尽量在 5 秒内采样。reset 不同或跨重置时重采；不能确认同账号则标无法比较。
3. 检查 Composer 和 rail 的候选数、适配器 ID、空间检查和实际截图。P0 标记不等于正式圆环 UI，几何 ready 不等于视觉验收通过。
4. 验证输入、发送、Tab/focus、原生菜单、任务切换、Composer/rail 重建、设置页、两主题、常见/最小窗口尺寸和缩放；记录失败与重试。
5. 禁用、热重载、再启用后确认没有旧标记和迟到日志；以无 `[data-cui-probe]` 残留作为清理的一项检查，而非全部验收。
6. P0 仅 Weekly 的真实账号暂时不可用时，明确该实机场景待测；数据层合成测试不能替代实机三处 UI 验收。

Windows 平台完整通过之后，再实施 P1 Store/Scheduler、P2 圆环与共享 Popover。macOS 与 ARM64 仍需分别验证。正式发布前还须按原方案完成 30 分钟使用稳定性观察、完整回归、安装/禁用/卸载/升级和平台兼容报告。

2026-11-06 第二次尝试也返回 close-timeout；已回读监督进程退出、原 Codex 主进程仍运行且 CDP 未启用。窗口关闭和不带 /F 的进程树退出请求均未使当前客户端退出。实际 Loader 会话仍未启动，不计为 P0 通过。后续需从客户端菜单明确选择“退出”使该进程结束，再启动已准备的固定 Loader；不重复安排同一失败流程。

后续复查发现主进程已更换，但新进程仍未启用 CDP。增加 `--wait` 入口，参数与 `--arm` 相同：启动独立监督进程等待所有 Codex 进程退出，最长 30 分钟，不发送关闭请求；正常退出后自动进入同一固定 Loader 运行时。此时测试者只需通过客户端菜单退出，等待 Loader 自动重新打开，不应再从普通快捷方式手动打开。`client-exit-wait-expired` 表示等待到期，需核对进程确已结束后再恢复；状态文件不能替代实际进程存活证据。
