# Codex Usage Indicator 技术验证与实施方案

日期：2026-11-05（Asia/Shanghai）  
依据：用户提供的 v1.1 策划文档，以及用户最新明确要求：兼顾 Pro 用户只有 Weekly 用量；只有 Weekly 时不显示任何 5H 数据和图标。  
状态：源码与协议验证完成；Windows/macOS 实机 P0 尚未通过。本文为实施建议，未将建议中的产品调整视为已批准。

## 1. 结论与边界

建议保留 TypeScript Renderer Plugin + Codex Script Loader + Renderer Usage Provider 主线。MVP 不引入 Rust Bridge，也不启动常驻 App Server。App Server 先作为独立探针和交叉验证工具；Renderer 不能直接派生本地进程，若其成为正式备用数据源，需要额外传输和宿主支持，应重新评估范围。

Pro 仅有 Weekly 是正常支持场景：Weekly 显示真实 Remaining 与 Reset at；Composer、Sidebar 和详情卡片均隐藏整个 5H 指标，不显示圆环、图标、标签、占位符或重置时间。Composer 单环居中，Sidebar 容器高度随单指标收缩，详情卡片仅保留 Weekly 分区。只要得到有效主账号 Weekly，连接状态即可为 Connected，数据可为 ready，coverage 为 weekly-only。不得因此报告连接故障，不得伪造 5H。该规则适用于所有套餐，不按套餐名猜测窗口。即使 planType=pro，只要真实返回 300 分钟窗口，也正常显示。

现有证据支持开展 P0 实机验证，尚不足以承诺双平台可发布。两个 UI 挂载点和当前账号真实额度均需目标客户端实测。

本轮只读检查项目与远端，在临时目录下载参考源码、导出协议并运行定向测试；未安装 Loader、未注入当前客户端、未重启 Codex，未修改项目文件或 Git/远端状态。

## 3. 已验证的技术事实

### 3.1 Loader 能力与限制

Schema v1 支持 renderer-only 插件。使用 module-style `module.exports = {start, stop}` 可接入生命周期；构建产物需满足 Loader 模块格式，不能直接假设浏览器 ESM `export` 会被识别。

新版包应包含 manifest.json、index.js、README.md、LICENSE，以及复用第三方代码时的 NOTICE.md；manifest 声明 documentation 和 settings.mode=none。MVP 若只用 DOM Adapter，仅申请 dom，不申请 storage、settings、composer、loopback-websocket。只有真正使用 Accessory 时才加入 composer。

`api.composer.registerAccessory` 存在，基础能力在上游文档中标注自 0.5.11 提供。但当前契约明确：挂载在已验证的 Composer flex 控制行中、原生模型控件之前。它不能直接满足“输入框下方双环”。最终位置坚持冻结设计时，需单独的 Composer DOM Adapter；不能通过给 Accessory 强设定位来假装满足契约。

Windows Native Runtime 是上游声明的主要实测路径；macOS Node 22+ runtime 已实现但上游仍注明没有 macOS 硬件验证。Windows ARM64 也必须独立验收，不能继承 x64 结果。

Loader 通过本地 CDP 调试会话加载脚本，并非 OpenAI 原生公开 UI 扩展 SDK。无需修改 app.asar，但运行与注入依赖 Loader 启动流程。CLI、MCP 或普通插件接口并不能自动成为任意 Renderer DOM 挂载接口。

### 3.2 Renderer Usage Service

Better UI 的实现依次尝试可选 IPC `usage-fetch`、发现当前 app:// 资源中的内部 HTTP 客户端并调用 safeGet、以及旧版 electronBridge 消息路径。

Loader 本次公开 Renderer API 列表没有通用 usage-fetch IPC 合同；不能把 Better UI 中对 api.ipc 的可选探测当成标准能力。

内部模块发现涉及入口资源、动态 import、导出对象/缓存遍历和 safeGet/makeRequest 能力识别；这些实现细节会漂移。`/wham/usage` 不能简单实现成 `fetch('/wham/usage')`，也不是 Renderer 可以不经认证直接访问的稳定公开 URL。

已确认参考源码使用的原始字段：

```text
rate_limit.primary_window / secondary_window
used_percent
limit_window_seconds
reset_at
```

因此 Provider A 先将秒时长映射为分钟，Provider B 接受 camelCase，二者分别校验，之后输出统一契约。只扫描主账号 rate_limit，不递归扫描整包，不读取 additional_rate_limits 来补齐。

参考实现存在不适合直接复制的行为：

- 按最接近 300/10080 分钟选择窗口，可能误标其他周期。
- `Number(null)`、`Number('')` 可变成 0，需要明确拒绝。
- applySnapshot 会沿用旧快照缺失窗口，可能把新旧响应混成一份。
- 部分注释和失败日志仍提及 DOM fallback，不能仅凭 README 判断每条代码路径。

本项目必须使用精确周期匹配和整份快照替换；页面文字不作为额度来源。

### 3.3 App Server

官方文档确认 initialize → initialized 握手，以及 account/read、account/rateLimits/read 和 account/rateLimits/updated。App Server 存在稳定与 experimentalApi 两类接口，不能笼统认为所有方法都必须开启实验能力；本项目探针只使用基础方法，按目标 CLI 协议验证。

本机实际导出的 RateLimitWindow Schema 为：

```typescript
interface RawAppServerWindow {
  usedPercent: number
  windowDurationMins?: number | null
  resetsAt?: number | null
}
```

响应同时存在兼容单池视图 rateLimits 与可空多池视图 rateLimitsByLimitId；新版本还可能提供 accountId。优先明确选主池 codex；旧版本仅在兼容视图归属可确认时使用 rateLimits。不能对多池视图任取第一个，也不能把两个视图各取一半合并。

独立 App Server 的通知不等于能订阅 Desktop 另一个进程的全部额度变化。应按本连接的真实事件能力验收，并保留轮询。

Windows Usage Monitor 当前代码会对 planType=pro 主动不给 5H、Weekly 接受约 6–8 天区间。本项目不照搬这两个策略：严格根据返回的 300/10080 分钟窗口决定展示。

## 6. 推荐实现方案

### 6.1 技术栈与复用

TypeScript + Bun 管理依赖、构建和打包；发布单个自包含 CJS 格式 index.js，源码与生成物分离；原生 DOM/SVG，局部命名空间 CSS。不引入 Nuxt/Vue/Nuxt UI：当前是注入现有应用的独立微型组件，没有 Nuxt 宿主或已有组件体系，引入整套应用框架会扩大包体和集成面。

复用 Loader 官方示例的 manifest、生命周期和卸载约定；Better UI 的 MIT 代码仅提取必要的 HTTP 能力识别思路或经过审查的小模块，保留版权和 NOTICE，不引入其完整 UI、账号模式检测、其他内部配置读取或 native Usage 隐藏逻辑。

Popover 定位建议使用固定版本的 @floating-ui/dom（computePosition、offset、flip、shift、autoUpdate），业务 Hover/Click 状态机自行实现。原生 Popover 可进一步验证，但不能假设目标 Electron 一定满足所有 CSS Anchor/层级约束。Floating UI 是定位依赖，不是额外 UI Framework；只在卡片打开时注册 autoUpdate，关闭时清理。

SVG 圆环、Remaining 转换、快照替换和插件调度属于本项目的小型业务实现；通用定位、打包、测试不重造。主要维护成本集中于两个 DOM Adapter 与内部 HTTP 能力发现，应独立版本化。

### 6.2 模块边界

```text
Loader lifecycle
  -> RendererCapabilities（内部 HTTP 能力探测）
  -> WhamProvider -> validate/normalize -> UsageStore
  -> RefreshScheduler（唯一请求入口）
  -> ComposerAdapter / RailAdapter -> RingViews
  -> SharedPopoverController -> Floating UI positioning

独立 P0 工具：AppServerProbe -> AppServerNormalizer -> 脱敏对照结果
```

Provider、Normalizer 和 Store 不依赖 DOM；Adapter 不发请求；Popover 从 Store 订阅同一快照。MVP 仅创建 Renderer Provider，App Server 运行模块放 tools/probes，不作为运行包的假备用实现。

### 6.3 建议统一契约

```typescript
type Source = 'renderer-wham' | 'app-server'
type Coverage = 'both' | 'five-hour-only' | 'weekly-only' | 'none'
interface UsageWindow {
  remainingPercent: number | null
  resetsAt: number | null // Unix 秒
}
interface UsageSnapshot {
  status: 'ready' | 'stale' | 'unavailable' | 'unauthorized'
  connection: 'connecting' | 'connected' | 'disconnected'
  quality: 'normal' | 'degraded'
  coverage: Coverage
  fiveHour: UsageWindow | null
  weekly: UsageWindow | null
  fetchedAt: number | null // Unix 秒，最后有效额度快照取得时间
  source: Source
}
```

内部控制器另持有 generation、账号上下文标识、最后响应时间、有限诊断码，不把原始账号信息传到 UI。覆盖率由识别出的窗口推导；quality=degraded 不用于单窗口缺失。连接成功并且只有 Weekly 是 ready/connected/normal/weekly-only。

启动没有快照时 connecting/unavailable；401/403 归类 unauthorized；网络错误保留同一账号最近有效快照并更新 connection；超过 90 秒再转 stale。账号更换或身份归属不确定时立即清掉旧值并递增 generation，旧响应即使完成也不得提交。

成功响应中窗口缺失，应整份替换并清空消失的窗口。请求失败才保留旧快照。成功返回但没有任何受支持额度是 unavailable，不得刷新旧额度的 fetchedAt 让旧值看起来变新。错误通知与旧快照的新鲜度分别表达。

### 6.4 Normalizer 规则

1. 必须验证对象路径和字段类型。null、undefined、空字符串、布尔值、NaN/Infinity 不是有效数字；不对未知值盲目 Number()。
2. Renderer 仅匹配 limit_window_seconds=18000 和 604800；App Server 仅匹配 windowDurationMins=300 和 10080。
3. primary/secondary 顺序不具有业务意义；duration 缺失即不归类。其他周期记录有限诊断，不强贴 5H/WEEK。
4. 同时存在重复同周期窗口且无法唯一归属时，相关窗口置未知并记录 schema/ambiguity，不任取一个。
5. 有限 usedPercent 按文档进行 100-used 并 clamp 到 0..100；越界值同时记诊断。圆环和数字共享同一用于展示的百分比，避免环与数字口径不同。
6. reset_at/resetsAt 必须为有效的 Unix 秒，缺失不计算；不使用 reset_after_seconds 或本地 token 推测；过去的重置时间不自动把额度变成 100%。
7. 不根据套餐硬编码窗口。Pro 只有 Weekly、Pro 有两个窗口、其他套餐只有 Weekly 都按响应真实覆盖率处理。
8. 任何一次输出均来自同一 Provider、同一账号上下文、同一次响应，不沿用旧窗口补齐。

### 6.5 刷新与状态

初始化即刷新，成功后安排约 30 秒轮询；焦点、visibility 恢复和已验证通知触发合并刷新。只允许一个 in-flight 请求和一个轮询定时器。短时间事件防抖，进行中的普通刷新复用 Promise；账号变化必须作废旧 generation，并在旧请求取消/结束后保证重读新上下文。

使用超时与取消；底层不支持 Abort 时仍要隔离迟到响应。单独安排新鲜度到期检查，不能仅靠网络请求返回时计算 stale。系统休眠后第一时间重算年龄并触发刷新，pending 请求不能永久锁死。

429 尊重 Retry-After；持续错误采用有上限退避，建议上限 5 分钟。正常态仍为 30 秒，恢复前台也不能绕过服务端限流。需要把异常退避明确写入验收规则，避免与“任何情况严格 30 秒”产生冲突。手动刷新按钮仍不提供。

无稳定事件通道时，P0 明确报告 polling-only；不为模拟事件驱动而启动第二个进程。不要宣称采样数据为实时流；LIVE 建议只在“连接成功且数据新鲜”的意义下使用，卡片提供实际更新时间。

### 6.6 UI 与生命周期

Composer 仅绑定唯一、可见的编辑器外围容器；新增 sibling 区域，不修改 contenteditable 内部，不注册提交上下文，不改变输入和发送行为。若没有安全空间，仅报告不兼容，不偷偷移到模型菜单内。

Rail 候选优先 nav[data-app-navigation-rail]；旧布局的 app-shell-left-panel 等只作为独立兼容规则。参考项目的 Usage 主要是宽侧栏底部 slot，且其 rail 逻辑包含隐藏原生 Usage，本项目不能把该测试当成 68px Icon Rail 挂载证明，也不照搬隐藏行为。

两个 Adapter 都需要唯一候选验证、可见性检查、语义位置检查和空间检查。缺失/多候选/空间不足时不插入；窄屏、原生菜单展开、设置页和无 Composer 页面分开处理。UI 失败不污染数据连接状态。

Observer 先发现挂载点，再缩小观察范围；过滤无关聊天变化，防止插件自身更新触发无限重新扫描。不使用随机 class 或固定屏幕坐标作为定位规则。尺寸测量可用于验证空间，不能用来猜一个坐标强行插入。

一个 document 一个 Store/Scheduler/Popover；start 可重复、stop 幂等。资源创建后即登记 disposer，启动中途失败也能清理。stop 先递增 generation 并取消请求/定时器，再移除卡片、Observer、监听器、样式和两个插入节点。并排窗口各自运行不能假称全应用只有一个调度器；跨 Renderer 协调暂不增加。

卡片状态为 closed / transient / pinned，四个圆环入口共享同一实例。键盘 focus 可预览，Enter/Space 可固定，Escape 关闭并返回触发点；卡片内有焦点时不因鼠标离开而关闭。鼠标跨过入口与卡片的小间隙应有短延迟。点击另一个入口切换锚点，点击当前固定入口解除固定；outside 关闭。

入口使用 button 与 aria-expanded、可访问名称；SVG aria-hidden，可访问名称说明周期和剩余比例。只有 Weekly 时不创建 5H 按钮、SVG、标签或详情分区，Tab 顺序和可访问性树中也不保留 5H 占位。窗口存在但百分比缺失时仍可显示该窗口的未知状态；不能把初始化或请求失败当作服务端已确认不存在该窗口。不对每 30 秒正常采样制造屏幕阅读器播报。

颜色保持 5H 蓝青、Weekly 紫；告警阈值基于原始数值，采用 >=50、>=20、>=10、否则危险，避免小数区间断档。警告信息除颜色之外保留文字提示。主题复用目标版本真实语义变量，CSS 命名空间隔离，探测不到 token 时提供有限 fallback，不从外站加载样式。

时间：系统时区 + 绝对日期/时间/UTC offset；Unix 秒只在 Date 边界乘 1000。若严格英文格式，通过 en-US + formatToParts 组装；测试 Asia/Shanghai、UTC、America/New_York 的夏令时边界以及非整点 offset，不推测缺失时间。

## 7. P0 实机验证方案与退出门槛

### P0-A：本轮已完成的证据

固定源码版本、核查 Loader 合同、明确内部 HTTP 访问链、导出 CLI Schema、运行相关上游定向测试、记录失败与环境限制。

### P0-B：Windows x64 真实探针

在可写原生 Windows 开发会话完成，不使用本次 WSL 结果替代：

1. 记录 Codex 版本/build、Loader 版本/commit、OS/架构、主题、缩放和 UI 语言。敏感账号标识仅内存比对，输出不含账号/email/token。
2. 安装已审阅的固定版 Loader，正常会话允许时启动测试客户端。探针关闭时完整恢复。
3. 单独运行能力探针：HTTP 客户端候选数、所选适配器 ID、请求是否成功、结构版本。仅允许固定 GET /wham/usage，不开放任意 URL/RPC。
4. 输出白名单样本：两个原始窗口的 duration、used、reset，加 Provider 和采集时间；缺失保留 null，不导出整个响应。
5. Composer 与 rail 各挂一个只读、可撤销测试元素，验证原生边界尺寸、无遮挡、Tab/输入/发送行为、切换任务及重建。不能把“DOM 节点存在”当视觉通过。
6. 独立 App Server 探针只发 initialize、initialized、account/read(refreshToken=false)、account/rateLimits/read，保持 stdin 到响应后再结束进程。不创建线程、不调用 turn、不调用登录或 reset-credit consume。
7. 比对两个探针和原生 Usage。账号/工作区归属确认后，尽量在 5 秒内采集；reset 不一致或跨重置时不判冲突，重新采样。记录请求时间与成功取得时间，不能把 fetchedAt 当服务端测量时间。
8. Pro 仅 Weekly：Weekly 数值和 Reset at 对齐原生；三处 UI 不显示任何 5H 圆环、图标、文字、数值、占位符或重置时间；布局随单窗口收缩；connected/ready/normal；热重载或从有 5H 的旧账号切换后仍不残留旧 5H。

一致性检查不需要在生产每 30 秒双查。无充分同账号证据时仅记录“无法比较”；同周期、同 reset、相近采样且差异重复出现后才记录冲突。冲突阈值作为 P0 观测结果制定，不能把正常消耗差值直接标记 degraded。

### P0-C：macOS Apple Silicon 与 Windows ARM64

macOS 使用固定 Node 22+ runtime，逐项重复 P0-B，并专项验证启动监督、退出清理、缩放、主题、Popover 位置和包路径校验。模拟 macOS 单测不计硬件证据。Windows ARM64 单列矩阵，同样验证 Native Host 包与目标架构。没有设备就保持待验证，不标兼容通过。

### Go / No-go

- 某平台拿到可确认归属的主账号至少一个真实窗口，两个插入位置均可安全挂载，且启停/重建不会破坏原生行为，才允许该平台进入 P1/P2 整合。
- 完整双平台 v0.1.0 必须 Windows 与 macOS 各自通过；ARM64 宣称支持也必须有对应证据。
- Pro 缺少 5H 不阻止通过；不得把“不需要伪造第二窗口”改成“必须总有两份数据”。
- Renderer 无法读真实主池时先停止该平台实施，评估已有宿主能力或 App Server 传输；不直接上 Rust。
- 安全挂载位置不存在、只能覆盖发送按钮、只能依靠凭据文件或修改安装包才能工作时，P0 不通过，需要重新确认边界。

交付应包含平台报告、脱敏字段样本、UI 截图、锚点候选与唯一性结果、stop 后残留检查、限流/网络错误结果。当前这些实机交付物尚未生成。

## 9. 必须覆盖的测试与运行验收

数据用例：双窗口、仅 Weekly、仅 5H、Pro 三种覆盖组合、primary/secondary 交换、额外模型包含完整双窗口但主池为空、缺失 duration、重复 duration、null/空串/NaN/Infinity、0/100/越界 used、reset 缺失/无效/过去、成功响应移除窗口；只有 Weekly 时三处 UI 和可访问性树均不存在 5H；单窗口与双窗口切换时布局、焦点及已展开卡片正确更新。

调度用例：初始刷新、30 秒、焦点与 visibility 合并、请求永久挂起超时、stop 后迟到响应、start-stop-start、跨账号旧请求回写、90 秒独立 stale、离线恢复、429 Retry-After、系统休眠恢复。用假时钟验证，无需真实等待 90 秒。

UI 实机：两主题、常见与最小支持窗口尺寸、系统缩放、键盘焦点、鼠标移入卡片、点击固定/切换入口、Escape/outside、任务切换/Composer 重建、rail 重建、设置页面、原生弹窗、热重载/禁用后清理。

性能验证限于实际风险：30 分钟正常使用中观察轮询次数、Observer 触发/扫描次数、DOM 节点数和监听器是否增长；这是兼容性稳定性验收建议，当前未运行。无需引入与用量指示器无关的大型压力矩阵。
